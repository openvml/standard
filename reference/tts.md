> **OpenVML — Open Voice Markup Language**
> 
> An open, declarative format for describing voice-driven audiovisual content, including dialogue,
> narration, scenes, media, timing, and synchronization.

# TTS Engine and Voice Resolution

**OVML Standard 2.2**

## 1. Purpose

OVML describes the speech content of a project. It does not require that speech be pre-rendered as a
file.

A character's voice is declared through the character definition.

The Player or TTS engine resolves the declared voice and produces the speech.

This document describes how TTS is declared, how voices are resolved, and how OVML avoids storing
credentials.

## 2. TTS Is Declarative

OVML references voices declaratively.

A plain OVML project may describe a character's voice without containing pre-rendered speech audio.

Example:

```xml
<character
    id="alex"
    name="Alex"
    voiceId="ru_RU-some-voice"
    voiceName="Russian Voice"
    voiceLang="ru-RU"
    voiceEngine="piper" />
```

The document describes which voice should be used.

The actual speech may be generated by the Player at runtime.

Conceptually:

```text
OVML
  ↓
Character
  ↓
Voice specification
  ↓
TTS Provider
  ↓
Generated audio
  ↓
Playback
```

This allows the same OVML scenario to remain small and independent from pre-rendered speech files.

## 3. Voice Attributes on a Character

A character may declare its voice through voice attributes.

Attribute	Type	Default	Description
voiceId	string	empty	Provider-specific voice identifier
voiceName	string	empty	Human-readable voice name
voiceLang	string	empty	Language identifier
voiceEngine	string	implementation-defined	TTS/voice engine identifier
pitch	float	1.0	Base pitch multiplier
rate	float	1.0	Base speech-rate multiplier

Example:

```xml
<character
    id="vestfal"
    name="Vestfal"
    voiceEngine="edge-tts"
    voiceId="en-US-GuyNeural"
    voiceName="Guy"
    voiceLang="en-US"
    pitch="1.0"
    rate="1.0" />
```

## 4. voiceEngine

The `voiceEngine` attribute identifies the TTS or voice engine associated with `voiceId`.

Examples may include:

edge-tts
elevenlabs
web-speech
piper

The standard does not restrict implementations to these values.

Applications MAY support additional engines.

Unknown engine identifiers SHOULD be preserved when an OVML document is read and written.

## 5. voiceId

The `voiceId` attribute identifies the requested voice.

voiceId="en-US-GuyNeural"

The meaning of `voiceId` depends on `voiceEngine`.

The OVML Standard does not define a global namespace for voice identifiers.

Therefore, implementations SHOULD interpret the voice reference as:

voiceEngine + voiceId

## 6. voiceLang

The `voiceLang` attribute specifies the language associated with the voice.

Examples:

en-US
en-GB
ru-RU
uk-UA
de-DE
fr-FR

Language identifiers SHOULD follow BCP 47 conventions.

The standard does not require an implementation to support every language.

The per-voice language may differ from the document-level language.

## 7. Provider Resolution

The Player resolves a voice reference through the TTS provider.

For a built-in provider:

```text
OVML
  ↓
voiceEngine + voiceId
  ↓
Player
  ↓
Built-in TTS provider
```

For a user-provided provider:

```text
OVML
  ↓
voiceEngine + voiceId
  ↓
Player
  ↓
User's credentials
  ↓
External TTS provider
```

Credentials belong to the execution environment, not to the OVML document.

## 8. Built-in TTS Providers

An OpenVML Player may provide built-in TTS providers that do not require the user to enter an API
key.

Examples may include locally available or otherwise supported providers such as:

- Piper;
- Coqui;
- Edge TTS;
- other providers supported by the Player.

Availability depends on the Player implementation and target platform.

When a voice belongs to a built-in provider, the OVML document only needs to identify the provider
and voice.

```xml
<character
    id="narrator"
    name="Narrator"
    voiceId="ru_RU-some-voice"
    voiceLang="ru-RU"
    voiceEngine="piper" />
```

No secret credentials are stored in the OVML document.

## 9. User-provided TTS Providers

A Player may also support commercial or external TTS providers.

Examples include providers requiring user credentials or API keys.

The OVML document may identify the required provider and voice:

```xml
<character
    id="maria"
    name="Maria"
    voiceId="provider_voice_id"
    voiceLang="en-US"
    voiceEngine="elevenlabs" />
```

The required credentials are not part of OVML.

## 10. Credentials MUST NOT Be Stored in OVML

OVML MUST NOT contain:

- API keys;
- access tokens;
- passwords;
- private keys;
- provider secrets;
- authentication cookies.

For example, the following is invalid as a project design:

```xml
<character
    voiceEngine="elevenlabs"
    apiKey="secret-value" />
```

Authentication belongs to the Player, Studio, or another execution environment.

This separation allows an OVML document to be shared without exposing the author's credentials.

## 11. Free and Built-in Voices

A Player MAY provide voices that can be used without user-supplied API credentials.

Such voices may include:

- local voices;
- system voices;
- bundled voices;
- free remote voice services;
- other voices provided directly by the Player.

The absence of an API key does not prevent an OVML document from being a valid document.

Voice availability is a runtime capability of the Player.

## 12. Unspecified Voices

A character MAY be defined without voice information:

```xml
<character
    id="alex"
    name="Alex"
    gender="male"
    age="adult"
    role="main" />
```

Such a document is valid.

The OVML Standard does not prescribe a default TTS provider or default voice.

When voice information is absent, the consuming application determines how the character's speech is
resolved.

Failure to resolve a requested voice is a runtime/provider condition and is not, by itself, a
structural OVML validation error.

## 13. Pre-rendered TTS

Speech may instead be represented as a pre-rendered audio asset.

An OVMZ package MAY contain pre-rendered TTS audio.

For example:

```text
tts/
├── narrator/
│   ├── line-001.wav
│   └── line-002.wav
└── alex/
    ├── line-001.wav
    └── line-002.wav
```

The script may reference the generated audio through a project asset ID:

```xml
<audio src="tts/chapter01-line004.wav" />
```

The TTS audio is generated during the export/build process.

Playback of a completed OVMZ does not normally require access to the original TTS provider.

This is especially useful for:

- offline playback;
- reliable distribution;
- archival;
- sharing projects with users who do not have the required TTS provider;
- avoiding repeated synthesis during playback.

The process is:

```text
OVML
  ↓
TTS synthesis
  ↓
WAV/audio resources
  ↓
OVMZ
```

## 14. Runtime TTS vs. Pre-rendered Speech

A plain OVML project may rely on runtime TTS.

An OVMZ project may contain pre-rendered speech.

An OVMV project has already rendered speech into the final audio.

Feature	OVML	OVMZ	OVMV
Runtime TTS	Yes	Optional	No
Pre-rendered TTS	Optional	Yes	Included in final audio

## 15. TTS and Audio Processing

Generated speech is logically an audio resource.

A Player or authoring system may apply an audio-processing preset to the generated speech.

A character may reference an audio-processing preset through its configuration.

Example:

```xml
<character
    id="vestfal"
    name="Vestfal"
    audioProcessorId="preset_1"
    audioProcessorName="Warm Voice"
    audioProcessorFile="presets/audio/WarmVoice.ovml" />
```

The processing preset is separate from the voice declaration.

## 16. Validation vs. Runtime

An OVML validator SHOULD verify the structure of the voice declaration.

It does not determine whether:

- a TTS provider is available;
- a voice exists at runtime;
- an API key is valid;
- a voice preset is available;
- a particular Player supports a requested voice engine.

These are runtime or implementation concerns.

## 17. Design Principle

OVML separates the character from the voice, and the voice declaration from the credentials.

Character defines who the speaker is.

Voice configuration defines how the character's voice is requested.

The Player determines how the speech is produced.

This allows the same OVML document to be used by different Players, TTS engines, operating systems,
and rendering environments.
